# GASを介さない接続方式の比較計画

作成日：2026-11-04 JST。状態：比較計画とWorkers＋D1の初段階ローカル試作。クラウド実測・採用は未実施。試作済み範囲と未実装事項は[試作README](prototype/README.md)を参照。

最優先条件（利用者指定）：**このプログラムのための追加支出を0円にする。** 利用頻度は高くなく、速度改善のための月額課金は行わない。既に契約しているChatGPT Proに付随するAPIクレジットは、追加支出なしの範囲で活用してよい。

## 今回の判断

**追加支出0円で継続できる構成だけを候補にする。** その中でWorkers＋D1のローカル試作を先に行い、Firestore直結は無料プランでの保存契約と検索の成立性を先に検証する。これは試作の順番であり、移行先の決定ではない。無料枠の上限に当たった場合は停止・取得頻度の削減・現行構成の継続を選び、有料プランへ移行しない。

現行の配信内一覧は成功時でも往復中央値2.811秒で、30秒タイムアウトも1回あった。詳細な条件・限界は[開発ログ](DEVELOPMENT_LOG.md)に残している。画面をアプリで包むだけでは同じGAS呼び出しが残るため、まず通信先そのものを比較する。

SQLは掲載履歴と手動履歴の分離、検索、版数の条件付き保存を表現しやすい。一方、Firestore直結では共通APIの運用を省ける可能性がある。最大100件の保存と配信確認完了をクライアントの申告だけに依存せず検証できるか、検索のためにどれだけ取得するかが判断点になる。この適性評価は現行コードと以下の公式仕様からの設計上の推論である。

## 比較する構成

| 比較点 | A：Firestore直結 | B：本人認証付きWorkers API＋D1 |
| --- | --- | --- |
| 画面からの経路 | Web／Apple SDK→Firestore。GASなし | HTTPS→Worker→D1。GASなし |
| 本人認証の試作案 | Firebase AuthenticationのGoogleログイン＋許可した本人UIDのRules | 同じFirebaseのID tokenをWorkerで検証し、本人UIDを許可。DB資格情報は端末へ配布しない |
| 手動保存の検証場所 | Security Rulesとtransaction。クライアントコードだけに依存しない検証が必要 | API入力検証＋DB内の条件・制約。同時更新で検証後に条件が変わる場合も拒否 |
| Python同期 | Python SDK＋専用のサーバー認証/IAM。既存のDrive用OAuthだけでは接続できない | 専用の同期API。PythonはD1の汎用SQL APIへ直接書き込まない |
| 履歴・関係 | ドキュメント参照・投影の設計が必要 | 主キー・外部キー・SQLで扱う設計 |
| 部分文字列検索 | Standardでは全検索用メタデータ取得＋ローカル絞り込みを最初の候補にする。初回取得量を含めて評価 | 正規化済み列に対する`instr`等のSQLで候補抽出。走査量を測る |
| 保存＋確認完了 | transaction内で一括確定する案。Rulesと件数上限が成立するかを先に検証 | D1の`batch`内で一括確定する案。全件検証を同じ原子的処理に含める |
| 運用 | Rules、索引、IAM、SDK、投影の整合性を管理 | API、SQL migration、認証、同期用資格情報を管理 |
| 将来のオフライン | 今回は明示的にサーバー確定を待つ。SDKのローカル反映と保存成功を混同しない | 今回はオンライン専用。端末保存・再接続キューは後の設計 |

Firestoreのモバイル／WebアクセスはAuth＋Rules、Python等のサーバーSDKはIAMで制御される。[Firestoreのアクセス制御](https://firebase.google.com/docs/firestore/security/overview)

Workerでの認証は単なるJWTのdecodeで済ませない。Firebase公式の検証条件に従い署名、期限、発行元、対象project、UIDを確認し、本人以外・未認証・別projectのtokenを拒否する。実装時はWorkersで動く検証ライブラリを選定し、鍵取得・更新、token更新・ログアウト後の挙動も試す。ブラウザーからの変更要求は許可OriginとContent-Typeも制限する。Mac／iPadのネイティブログインが成立するかも、アプリ本体の開発前に確認する。[ID token検証](https://firebase.google.com/docs/auth/admin/verify-id-tokens)

Python同期には本人ログインのtokenを流用しない。Bの最初の案は同期パスだけをCloudflare AccessのService Authで保護し、Workerでも検証済みのサービス識別を確認する。手動保存パスでは同期資格情報を拒否し、同期パスでは更新可能なメタデータ種別を限定する。ローカル試作の偽認証をクラウドへ持ち出さない。[Service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/)、[Accessの検証](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)

### Aで最初に確かめる点

- メタデータは不変の世代別collectionへ書き込み、検証後に有効世代ポインターを条件付き更新する。手動状態・追記履歴は世代の外へ置く。画面は要求ごとに世代を固定し、保存transactionは現在のポインター・対象配信版を再確認する。同期途中で新世代を見せない。
- メタデータ、現在のPMID状態、操作履歴、現在の配信確認、配信操作履歴を分離する。現在値の更新と履歴追記、操作IDの登録をtransactionで結び付ける。1文書に全メモ・全履歴を詰め込まない。
- 単純にPMIDごとの現在値＋履歴の相互検証を増やすと、Rulesの参照上限に触れる可能性がある。100件の異なる状態・メモ、共有PMIDを含む配信の未確認0件判定、操作IDと履歴の対応を、改変したクライアントからも破れない形で検証する。必要なら小さな集約単位を検討するが、巨大な本人専用1文書で回避しない。成立しなければ「直結は今回の契約に不適合」とし、保存APIを加える案は別構成として比較する。
- PythonのIAM権限とブラウザーのRulesは別物。Rulesでメタデータ書き込みを禁止しても、Pythonの誤った手動履歴更新を防いだことにはならない。同期処理の更新先制限・履歴不変テストを用意する。

Firestore transactionは原子的で、競合時に処理が再実行され、オフラインでは失敗する。Rulesは原子的操作全体で20回、各操作でも10回の文書アクセス上限があり、一部の参照はキャッシュされる。100件保存が必ず不可能とは断定せず、実際のRulesで確認する。[transactionとRulesの制限](https://firebase.google.com/docs/firestore/manage-data/transactions)

### Bで最初に確かめる点

- メタデータは世代ID付きのpapers／appearances／issues／candidates／texts、手動状態はreview_current／review_events／issue_review_current／issue_review_events、操作単位はoperationsへ分ける案とする。外部キー・一意制約を設け、現在値と履歴を同じbatchで更新する。
- `batch`の前にWorkerでSELECTしてから無条件UPDATEするだけでは競合を防げない。同期版・内容版・全期待版数・所属・未確認0件の検証をbatch内へ含める。条件付きUPDATEが0行でもSQLエラーではないため、0行を成功扱いしたまま後続をcommitしない。制約／trigger等で不成立時にbatch全体を中止する方式を小さく実証する。
- 本文を含む同期は未公開世代へ分割転送し、件数・ハッシュを確認した後、旧ポインターの期待値を条件に公開する。失敗したアップロードは非表示のまま。同じ同期IDの再送は重複しない。既存Pythonの`merge_payload`の和集合・訂正版保持を利用し、レビュー表を置換しない。
- 初期試作はread replicaを使わず、保存後に確定した現在値を返す。性能調整を加える場合も、再試行や別端末からの読み取りの整合性を改めて確認する。

D1の`batch`は複数SQLを順に実行し、途中のSQLエラーで一括rollbackする。この仕様だけでアプリの期待版数検証まで自動的に保証されるわけではない。[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/)

### 検索を同じ意味で比べる

比較用の正解は既存`Ledger.query`の結果とする。大文字小文字、1文字、日本語、数字の途中、`%`・`_`・引用符、空白、非BMP文字、別掲載履歴の分野＋日付を含む。検索語をSQLへ連結しない。SQLの`LIKE`のワイルドカードやSQLite標準の小文字化だけで、JSの部分一致と一致したとはみなさない。

Aでは要約・メモを含まない検索用メタデータを世代ごとに全取得し、既存と同じJSの絞り込みを行う最小案から始める。全件取得を済ませてからの検索時間だけでBと比べず、初回バイト数・取得時間・同期後の再取得も含める。Bも`instr`等による走査の費用・遅延を測る。両案とも状態条件・並び順・分類件数に必要な手動状態の取得量を計上する。

Firestoreのネイティブtext searchはEnterprise要件であり、単語検索と任意部分文字列の互換性は別途確認が必要。Standardの無料枠と混ぜて見積もらない。最初の試作では外部検索サービスやn-gram索引を追加しない。[Firestore text search](https://firebase.google.com/docs/firestore/enterprise/text-search)

## 架空データ試作の範囲と手順

### 1. 共通データと契約試験

新規ディレクトリ`pmid_ledger/prototype/`に隔離し、通常CLI・既存workflow・GASからは呼ばない。120 PMID・6配信の契約用データとD1保存の初段階を実装済み。以下の全比較項目が完了したものではなく、負荷用データは未実装。

固定seedと固定JST日付で、次の2種類を生成する。実台帳・`ledger_private/`・既存成果物・本番接続設定は読み込まない。架空であることを環境名と画面に表示する。

| データ | 規模 | 含める境界 |
| --- | --- | --- |
| 契約用 | 120 PMID、同一ID／別分野を含む6配信 | 0／1／51／100件編集、共有PMID、全5状態、訂正版、候補なし、日付不明、2000 UTF-16単位のメモ、長い分割本文 |
| 負荷用 | 5,000 PMID、200配信、10,000掲載履歴 | 重複掲載、訂正版、5万件の架空レビュー履歴、本文あり／なし、50件超の配信 |

Pythonの`Dataset`／`to_tables`で作るメタデータと、同じ入力を受けたGASのNode VM環境を正解データにする。既存テストを改変せず、比較対象のadapterを追加して利用者に見える結果を照合する。ローカルGASの所要時間は実サービス時間として比較しない。

| 必須ケース | 成功条件 |
| --- | --- |
| 配信一覧→配信内一覧→本文 | 状態・メモ・候補順・進捗・過去本文が一致し、一覧へ本文を返さない |
| 異なる状態・メモを100件保存 | 全件確定し版が1だけ進む。101件・1件だけ競合・所属外・不正入力では新規保存0件 |
| 保存＋確認完了 | 保存後に未確認0件のときだけ完了。変更0件の完了にも対応 |
| commit前の障害 | 新規履歴・現在値の変更0件。自動再試行でも入力内容を変えない |
| commit後の応答破棄 | 同じ操作ID・要求の再送で各履歴は1回だけ。保存確認前にUIを成功にしない |
| 2端末の同時保存 | 同じ期待版への異なる操作は一方だけ成功。もう一方は再読み込みを促し、上書きしない |
| 古い操作の再送 | 別端末の後続編集・配信再開を上書きせず、過去の操作成功と最新状態を区別する |
| 同期競合・再同期 | 世代混在なし、完了対象の内容変更は拒否。同じ同期入力は増殖せず、両操作履歴・メモ不変 |
| 同期の中断と再開 | 未完成の世代は見えない。公開済み内容を保持し、同じ同期IDで再開可能 |
| 権限の分離 | 未認証・別UIDは読書き不可。本人からのメタデータ更新、同期資格情報からの手動更新も不可 |
| TXT／CSV／JSON | TXT・CSVの契約一致。JSON→別TEST環境復元で件数・内容・版・全履歴・要求ハッシュ一致 |

新バックエンドの保存＋完了を1つの原子的transactionにできれば、GASで起こる新規操作の部分成功をなくせる。ただしこれは挙動の改善として明示し、GASの2段階失敗を無理に再現しない。旧GASの部分成功データを移す場合は履歴を保持する別の移行試験が必要。

### 2. ローカルで成立性を確認

1. BはMiniflareのworkerd／ローカルD1で、全件競合検証とrollback、操作ID再送、世代公開の最小ケースを実装した。Wrangler CLIは追加せず同じローカル実行基盤を直接利用する。SQLite単体の成功だけでD1成功とはしない。[MiniflareのD1 binding](https://developers.cloudflare.com/workers/testing/miniflare/storage/d1/)
2. AはFirestore／Auth EmulatorとRulesテストで、本人・別人・100件保存・配信完了を検証する。Admin SDKでテストが通ってもRulesの検証には数えない。[Rulesのテスト](https://firebase.google.com/docs/rules/unit-tests)
3. 共通の小さなブラウザー画面に、配信一覧、配信内カード、編集、保存、保存＋完了、再読み込みだけを用意する。既存画面の全面移植やSwiftアプリ化は後にする。
4. Pythonの架空データ同期adapterで、変更なし・訂正版追加・途中中断・手動保存と同時公開を試す。既存の毎時同期workflowには接続しない。

ローカル認証のモックは入力検証の試験に限る。クラウドAuthのログイン、失効、署名検証、IAM、実際のService Authはこの段階では未検証と表示する。

### 3. TESTクラウドで認証と往復を測定

ここからは別のTESTプロジェクト／DB、本人ログイン設定、同期用資格情報の準備が必要。ローカル段階を終えてから、課金を有効にせず利用できる設定対象と無料枠を確認する。Firestoreは課金を紐付けない無料プラン、Workers／D1もFreeに限定する。有料アカウントに紐付く従量課金環境は無料枠内の見積もりだけで使用しない。0円を保てる環境を用意できなければローカル検証までとする。既存GoogleプロジェクトへのAPI追加や公開サービスの作成は、本計画の作成だけで実施しない。

MacとiPad、家庭／職場回線の組合せごとに、同じfixture・ページ件数・検索条件・返却項目で測る。クラウド側の所在地、プラン、SDK版、コードcommit、データ件数を記録する。

- サインイン前から最初の利用可能画面までと、認証済み新規セッションからの最初の一覧を分けて測る。初回は各5回。サーバーのcold startを強制したとは表現しない。
- 反復は各操作30回、実行順を交互にし、別時間帯でも繰り返す。一覧、配信内一覧、本文、1／51／100件保存、保存＋完了、部分一致検索を対象とする。
- 反復の中央値・p95（nearest-rank）・最大、失敗数／全要求数、タイムアウト数と遅延応答を併記する。30回のp95は探索的な値で、長期的な障害率を推定しない。
- タップ→確定状態の描画機会までを総時間とし、認証更新・SDKの追加通信・再試行を含める。Worker/DB区間、読書き数、転送量も併記する。Firestoreのキャッシュだけの応答はサーバー確認済み応答と分け、最初の速度比較ではサーバー取得を要求する。
- 応答破棄・token期限切れ・二重送信・同期競合はTESTに限って注入し、正常系の速度と別集計にする。
- 計測記録は環境種別・操作種別・件数・時刻・時間・成否・読書き量に限定する。token、接続ID、検索語、タイトル、本文、メモは含めない。

**暫定の速度目標（利用者の合意済み要件ではない）：** 認証済みの一覧・配信内一覧・通常保存は中央値1秒以内／p95 2秒以内、100件保存＋完了はp95 3秒以内、認証済み新規セッションの最初の一覧は3秒以内。ログイン待ちは別計測。30秒級の要求や不明な保存結果が出たら原因と再試行結果を確認する。0円と保存の正しさを優先し、目標時間のために有料化しない。速度を満たしても契約試験に不合格なら採用しない。
