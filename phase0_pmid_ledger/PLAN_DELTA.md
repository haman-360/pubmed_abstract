# PMID確認台帳：承認済み計画への差分

2026-08-30。今回はPhase 0だけを実装する。本番移行・週次処理変更・既存Googleドキュメントへのリンク追加は別承認まで実施しない。

## 1. 配信時の内容を掲載履歴に保存する

Python＋GitHub ActionsとDrive JSONの正本を維持し、人の確認状態をGoogleスプレッドシートに分離する方針は変更しない。

将来の本番モデルは、PMIDごとの `Papers` と、`issue_id × topic_id × PMID` ごとの `Appearances` に分ける。掲載履歴には配信時タイトル、選定区分、配信日、分野、表示用日本語要約、一行評価、評価理由、重要度、復元元・出典、CURRENTリンクを保存する。必要に応じて配信情報を `Issues` に分離する。

- `automation_core.py:render_notebook_doc` の選定論文表示は `why_important`、`clinical_impact`、`practice_change_needed` を含む。将来の同期では、既存 `final` のこれらを見出し付きでそのまま保存する。新たな要約処理はしない。
- 候補表は選定候補だけではなく入力論文全体を含む。`scores[].one_line_assessment` と `total_score`、`outpatient_usefulness` を保存する。候補表掲載PMIDを取りこぼさない。
- JSONを優先し、残存するMarkdown/HTML/TXT、run成果物、必要な場合のみ既存文書の読み取りから復元する。本文内の明示的なPMIDとセクション境界で対応づけ、数字の単純抽出で関連付けない。
- CURRENTの本文は「現在版」。そこから過去の本文・配信日を推定して作らない。文書更新日時を過去の掲載日時として代用しない。根拠のない情報は空欄にし、復元状況を記録する。
- 掲載履歴の重複キーと内容ハッシュで冪等化する。同じ配信IDで内容が変わった場合は黙って置換せず、不一致として記録するか、明示的な訂正版履歴を追加する。後からの欠損復元も出典を保持する。
- 同期が書く書誌列と、人が書く `review_status`・更新日時・版数・メモを分離する。行全体を読み直して書き戻す方式は避ける。PMID重複防止と手動更新の競合防止を別々に設計する。
- Driveの `delivery_state` は機械処理の状態であり、レビュー状態を決める材料にしない。

過去の約1,013件は未検証の概数。事前調査ではローカル既知PMIDとDriveインデックスの和集合615件、ローカル過去成果物の抽出を含む候補集合961件を確認した。これらは異なる対象・時点の集計であり、1,013件の完全な復元と断定しない。Phase 1では読み取り専用の移行棚卸しで入力元ごとの件数・和集合・重複・未復元を出してから移行する。今回これらをTESTデータに取り込まない。

## 2. 初期画面は「最近の未確認」

| 区分 | 対象 |
|---|---|
| 最近の未確認（初期表示） | 直近3暦月の `unreviewed` |
| 原文入手待ち | 全期間の `want_fulltext` |
| 原文入手済み・未読 | 全期間の `fulltext_obtained` |
| 過去の未確認 | 3か月より古い `unreviewed`。日付不明も明示して収容 |
| 確認完了 | 全期間の `reviewed_no_fulltext` と `read` |

区分件数を表示し、1ページ50件。Phase 0は最大100件・掲載履歴300件までのTEST用。Phase 1で数千件の性能試験を別途行う。Phase 0の速度だけでは本番の性能を保証しない。

日付は日本時間で3暦月前を境界にする（90日固定ではない）。本番では最終掲載日、掲載がない場合は検出日の順に表示基準日を決め、根拠も表示する。分野・配信日の組み合わせ絞り込みは、同じ掲載履歴レコードで両条件を満たすか判定する。

## 3. Phase 0は独立したTEST Sheet＋本人限定GASのみ

8件の架空論文と8件の掲載履歴で、一覧・5状態の保存・詳細・リンク・TXT・保存失敗を検証する。状態変更はScriptLock、版数による楽観ロック、操作IDによる同一要求再試行を組み合わせる。状態・版数・日時・操作IDは隣接する4列への1回の書き込みとし、メモや掲載履歴には書かない。

固定TESTスプレッドシートID、名前、環境マーカーの一致を確認する。本人メールはScript Propertiesに設定し、ActiveUser/EffectiveUserの両方が一致しない場合は拒否する。公開設定はMYSELF、実行者はUSER_ACCESSING。認証できない環境で匿名公開に切り替えることはしない。

外部AI呼び出し、PubMed API、トリガー、Gmail、Drive JSON、既存Docs更新、GitHub Actionsへの接続コードは含めない。PubMedとCURRENT文書は、本人が押したときにブラウザで開くリンクだけを用意する。

## 4. OpenAI API不使用を恒久的な要件にする

台帳登録・移行・一覧・検索・絞り込み・状態変更・メモ・詳細・CSV/TXTはOpenAI APIを呼ばない。欠損要約・評価は空欄にする。既存の週次処理が生成済みの文章をコピーするだけであり、台帳のために同じ論文を再要約・再評価しない。

将来、AI再評価を追加する場合は別機能・明示的な操作とし、件数と入力/出力トークンに基づく想定API費用、上限額を提示して承認後に実行する。台帳の閲覧や同期に暗黙に組み込まない。

## Phase 1以降への順序変更

1. **Phase 0（今回）**：独立TEST環境、本人認証、iPad基本操作、要約履歴、TXTの成立確認。本番接続なし。
2. **Phase 1（未着手）**：本番スキーマ確定、読み取り専用棚卸し・移行dry-run、バックアップ、生成済み要約のコピー、冪等移行、週次同期と再試行、基本一覧・PMID/タイトル検索・状態変更。履歴詳細と5区分はこの時点で必須。
3. **Phase 2（未着手）**：詳細な検索・並べ替え、メモ編集、選択/全件TXT、CSVバックアップ、将来生成するDocsへのPMID指定の確認リンク。iPadからリンクを開き「原文入手希望」ボタンで保存する。GETアクセスだけでは状態を書き換えない。
4. **Phase 3（未着手）**：一括変更、操作改善、必要な場合のみ追加自動化。TXTのダウンロードを原文取得成功とは扱わず、`fulltext_obtained` へ自動変更しない。

既存の `poll_manifest` は終端runをスキップするため、台帳同期失敗を放置しない独立の再試行入口・同期記録が必要。Docs作成成功後の台帳同期失敗によって既存配信を失敗・再要約扱いに戻さない。本番Pythonの `drive.file` 認証から新しいSheetを操作できるかは、既存OAuthクライアントとのファイル認可とSheets API有効化を別途確認する。今回その認証情報・スコープ・Secretsは変更しない。
